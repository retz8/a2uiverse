# Upstream v1.0, multi-version agents and universal catalogs — research, 2026-11-01

What upstream A2UI holds for a v1.0 migration, for agents on more than one protocol version, and for catalog implementations not written in React — read on 2026-11-01 from `a2ui-project/a2ui` at `upstream/main` `825beac28` (2026-10-30), the published packages (`@a2ui/web_core` 0.14.0, `@a2ui/react` 0.14.0, `@a2ui/angular` 0.13.0, `a2ui-agent-sdk` 0.9.0, `a2ui-core` 0.4.0, `a2ui-a2a` 0.1.0), and both A2UIVerse repos as they stood. Each fact carries its file; a `path:line` without a prefix is under `typescript/` or `python/` of upstream, `a2uiverse/` paths are this repo's. "Measured" means run; everything else is read from code or documents. Phases 19, 20 and 21 of `_dev/TODO.md` cite this note.

### What v1.0 changes against v0.9.1
From `specification/v1_0/docs/evolution_guide.md` and the two A2A extension specs (`v0_9_1/docs/a2ui_extension_specification.md`, `v1_0/extensions/a2a/docs/a2ui_extension_specification.md`).

Wire:
- `version` is `"1.0"` (bare); v0.9.1 took `"v0.9"` or `"v0.9.1"`.
- `@path` and `@call` for bindings and calls, `@index` for the loop index (optional `offset`); a plain `path` or `call` key is literal data; unknown single-`@` keys rejected, `@@` escapes. ChildList templates and `updateDataModel.path` stay unprefixed.
- `callFunction` → `callRendererFunction`; new `agentFunctionResponse`, `callAgentFunction`, `rendererFunctionResponse`; `error` gains `functionCallId`, exclusive with `surfaceId`; error codes `UNALLOWED_PARENT`, `UNALLOWED_CHILD`.
- `createSurface` loses `theme`; may carry `components`, `dataModel`, `metadata.extensions` inline; `catalogId` optional (the surface's default). `ComponentCommon` and `FunctionCall` gain optional `catalogId`; `ComponentCommon` gains `metadata.extensions`; `Action.event` and the `action` message gain `userMessage`.
- `updateDataModel.value` required; `null` deletes the key.
- `allowedCallers` and `returnType` leave the wire `FunctionCall`; checked at runtime against the catalog.
- `AccessibilityAttributes` gains `live` and `hidden`, closes with `additionalProperties: false`.
- Terminology: client → renderer, server → agent; schema files renamed (`agent_to_renderer.json`, `renderer_to_agent.json`, `renderer_capabilities.json`, `renderer_data_model.json`, …).

Card and transport:
- Extension URI `https://a2ui.org/a2a-extension/a2ui/v1.0`; metadata keys `a2uiRendererCapabilities` (keyed `"1.0"`) and `a2uiRendererDataModel` (`version: "1.0"`); card `params` keep their flat shape (`supportedCatalogIds`, `acceptsInlineCatalogs`). MIME `application/a2ui+json`, as v0.9.1 already had.
- Basic catalog id `https://a2ui.org/specification/v1_0/catalogs/basic/catalog.json`; the file is `catalogs/basic/v1/catalog.json`.

Catalog schema:
- `protocolVersion` required (`"0.9"` assumed when absent; a v1.0 catalog says `"1.0"`); `$defs/theme` and `primaryColor` removed; `functions` a map by name; `FunctionDefinition` gains `allowedCallers` (`rendererOnly` default, `agentOnly`, `rendererOrAgent`) and `requiresUserActivation`; `ValidationResult` (`valid`, `code`, `message`, `severity`); catalog-level `instructions` replaces `rules.txt`; `$schema`, `$id`, `title`, `description` allowed; component, function and argument names and component instance ids are UAX #31 identifiers (#3414); `allowedParents` / `allowedChildren`; `"Surface"` reserved; `x-deprecated-reason`; a `$ref` may target only the catalog itself or `common_types.json`, never fetched.
- Basic catalog v1: the same 18 components and 14 functions as v0.9.1; `weight` explicit via `$defs/Weight`; `Video.posterUrl`; `TextField.placeholder`, `validationRegexp` removed (use `checks` with `regex`); `Slider.steps`; check functions return `validationResult`; `openUrl` sets `requiresUserActivation`; no `agentOnly` function.

Processing rules:
- Catalog resolution: the component's or call's own `catalogId`, then the surface default, then an error; no fallback to the advertised capabilities. "Catalogs authored for v0.9 cannot be used directly with v1.0 protocol runtimes"; "All mixed catalogs must use the same A2UI specification version" (`evolution_guide.md:15, 110, 152, 168`). Renderers "support simultaneous version handling … by inspecting the `version` property … to route payloads to version-specific controllers" (`:156`).
- `surfaceId` unique for the renderer's session; a remote call to a `rendererOnly` or unregistered function → `INVALID_FUNCTION_CALL`.

## 2. v0.9 and v0.9.1

### The difference on the wire
`git diff upstream/main:specification/v0_9 upstream/main:specification/v0_9_1`: byte-identical `catalogs/basic/catalog.json`, `rules.txt`, `json/common_types.json`, `client_capabilities.json`, `server_capabilities.json`, the four `*_list*.json`, `sample.json`. What differs:
- `version` in `server_to_client.json` (18/52/83/113), `client_to_server.json:9`, `client_data_model.json:9`: `"const": "v0.9"` → `"enum": ["v0.9", "v0.9.1"]`.
- Extension URI `…/a2ui/v0.9` → `…/a2ui/v0.9.1` (extension spec line 11); the spec's capabilities example keyed `"v0.9"` → `"v0.9.1"` (line 129) while both versions' capability schemas require the key `v0.9` (`client_capabilities.json:7-26`, `required: ["v0.9"]`, no top-level `additionalProperties: false`) — finding 12.
- `surfaceId` no longer "globally unique for the renderer's lifetime"; one sentence on the function execution boundary; v0.9.1 drops `catalogs/minimal/` and example 37; adds `docs/sdks_spec.md`. Every v0.9.1 JSON `$id` still says `specification/v0_9/`.
- `v0_9_1/docs/evolution_guide.md:27`: "v0.9.1 is fully compatible with v0.9 payloads … clients and servers can upgrade seamlessly." A valid v0.9 stream is a valid v0.9.1 stream; the reverse fails only on the version string.
- MIME: both documents say `application/a2ui+json`; the Python SDK writes the legacy `application/json+a2ui` for v0.8 and v0.9 messages and the new type for v0.9.1 and v1.0 (`a2ui_a2a/src/a2ui/a2a/parts.py:59-61`), and accepts both.

### Negotiation
- Card: `params` flat (`supportedCatalogIds`, `acceptsInlineCatalogs`), one `capabilities.extensions` entry per version; no spec says whether a card may carry several, and the Python helpers assume it: `try_activate_a2ui_extension` collects every card URI starting `https://a2ui.org/a2a-extension/a2ui`, matches them against the client's `X-A2A-Extensions` (or `message.extensions`), and activates the newest (`a2ui_a2a/src/a2ui/a2a/extension.py:96-181`). Activation is optional; otherwise the agent reads `message.metadata["a2uiClientCapabilities"]`. No spec gives a rule for choosing among versions.
- web_core: `Catalog(id, protocolVersion, …)` (`catalog/types.ts:728-833`; the legacy signature defaults to `'0.9'`); `protocolVersion` gates child-reference heuristics, `@index` and `ValidationResult` coercion, `path`/`call` versus `@path`/`@call`, UAX #31 checks, nested-call validation, the create-time version check. `DEFAULT_CATALOG_COMPATIBILITY` = `{'0.8':{0.8}, '0.9':{0.9,0.9.1}, '0.9.1':{0.9.1,0.9}, '1.0':{1.0}}` plus same-major from 1.0 (`adapters/base.ts:45-102`); a v0.9 and a v1.0 catalog coexist in one processor under different ids; `getRendererCapabilities(options)` writes every registered catalog id under every requested version key (`message-processor.ts:279-313`); `getRendererDataModel()` with no version throws when active surfaces span versions. web_core has no separate v0.9.1 basic catalog.
- Python: `ProtocolVersion` `V0_8="v0.8"`, `V0_9="v0.9"`, `V0_9_1="v0.9.1"`, `V1_0`; `_CAPABILITIES_ENTRIES` maps `V0_9_1` to the `"v0.9"` key; `resolve_catalogs` takes the version from the registered catalogs, not the client, reads that one key, and raises when registered catalogs read different keys (v0.9.x and v1.0 cannot share a processor; v0.9 and v0.9.1 can). `check_catalogs` rejects active catalogs whose `ProtocolVersion` members differ, `V0_9` versus `V0_9_1` included (`a2ui_agent/src/a2ui/inference_formats/_shared/catalogs.py:61-66`). `BasicCatalog(V0_9_1)` returns the v0.9 catalog with `protocol_version "v0.9"`, so it stamps `"v0.9"`; the SDK has no per-request version switch. The TypeScript agent SDK maps `v0.9.1` to `v0.9` the same way (`agents/a2ui_agent/src/utils/catalog-resolver.ts:33-36`).
- Samples: every upstream client keys `'v0.9'` only and sends `X-A2A-Extensions: …/a2ui/v0.9`; none uses the v0.9.1 URI. The Python ADK restaurant finder declares v0.8 and v0.9 entries on its card and picks per request from the header (`samples/agent/adk/restaurant_finder/agent.py:77-121`, `agent_executor.py:59`); the Node restaurant finder declares no A2UI extension (`samples/agent/node/restaurant_finder/src/index.ts:35-55`, `capabilities: {streaming: true}`), picks v1.0 from `a2uiRendererCapabilities["1.0"]` else v0.9 from `a2uiClientCapabilities["v0.9"]`, ignores a `v0.9.1` key, defaults to v0.9, stamps `"v0.9"` or `"1.0"` (`src/versions.ts:38-60`, `src/pick-a2ui.ts:41-64`). The community orchestrator merges its subagents' extension URIs into its own card and forwards the activated version's URI and the client's capabilities unchanged.
- Catalog versions (`docs/public/concepts/catalogs.md:416-433`): the client lists both ids; rebuilt agents prefer the new, older agents keep matching the old.

## 4. Catalog implementations not written in React

### Upstream's universal layer
- A catalog component is a `ComponentApi` — `name`, zod `schema`, optional `allowedParents`, `allowedChildren`, `metadata` (`core/web_core/src/catalog/types.ts:176-196`); no framework in it. Two implementation kinds: React's `ReactComponentImplementation` (`render`, `view?`; `renderers/react/src/react_component_implementation.ts:56-73`) and `WebComponentImplementation` = `{...api, tagName: string, element: CustomElementConstructor}` (`core/web_core/src/universal/web_component_implementation.ts:26-33`), recognised by shape (`is_web_component_implementation.ts:25-34`). `ReactCatalogComponent` is the union of the two.
- The element contract, `A2uiWebComponentElement` (`universal/a2ui_web_component_element.ts:28-48`): `context?: ComponentContext` ("an assignment is the signal to (re)bind") and `node?: ComponentNode` (wins when both set). Data arrives as JS properties, never attributes or slots. `ComponentContext` carries `componentModel`, `dataContext`, `surfaceComponents`, `theme` (= `surface.theme`), `dispatchAction`; `ComponentNode` carries `props: Signal<…>` with `ResolvedBinding`s, action closures and child `ComponentNode`s. Binding: `GenericBinder(context, schema)` from `@a2ui/web_core/v0_9`, or `node.props` (on `main`, #3705). Children: the element creates `document.createElement(childImpl.tagName)` and assigns `node`/`context` (`universal/render-a2ui-node.ts:32-115`, or by hand per `docs/public/guides/authoring-universal-components.md:580-627`). The tag is defined by the host through `registerUniversalElement`, which throws for a different class under a defined tag (`universal/register_universal_element.ts:33-57`).
- `universal/index.ts` exports `A2uiLitElement` (`@experimental … subject to change as A2UI transitions to the unified Node Layer resolution pipeline`, `a2ui-lit-element.ts:55-56`), `A2uiController`, `registerUniversalElement`, `isWebComponentImplementation`, `renderA2uiNode`, the two types; reached as `@a2ui/web_core/universal` and `/v0_9/universal`, not from `/v0_9` itself. `src/v0_9/universal/README.md:3`: "components can be registered directly into Lit, React, and Angular A2UI catalogs without framework-specific adapters"; the guide: "write a custom UI component once as a Web Component and use it directly across Lit, React, Angular, and more" (PR 2503, 2026-10-14; not in the 0.14.0 tarball).
- The basic catalog is 18 such elements since react 0.13.0 (`a2ui-basic-button`, `a2ui-card`, …; `v0_9/basic_catalog/components/index.ts:59-82`), light DOM (`createRenderRoot() { return this; }`); `A2uiLitElement` itself renders into a shadow root. Light-DOM `static styles` are rewritten (`:host` → the tag) and adopted once per root into `document.adoptedStyleSheets` (`a2ui-lit-element.ts:116-227`); in 0.14.0 a shadow-DOM subclass's styles are adopted into the document too (fixed by #3666, unreleased). Tokens: `injectBasicCatalogStyles()` adopts one `--a2ui-*` sheet under `:where(:root)`, `.a2ui-dark`, `.a2ui-light`, reaching shadow roots by inheritance. No provider or per-catalog scope exists in web_core; theme is the surface's.
- `@a2ui/react` 0.14.0 hosts a custom-element entry with no React code in the catalog: `prepareCatalogs` leaves such entries alone; `ChildElement` renders `'render' in impl` as React, anything else as `WebComponentNode` — `registerUniversalElement`, `React.createElement(tagName, {ref})`, `context`/`node` assigned in the ref callback and an effect (`web_component_node.tsx:60-109`); React and custom-element entries mix in one catalog (guide line 265; the explorer's `demoCatalog`). The reverse direction, `to_web_component.tsx`, wraps a React entry as `a2ui-react-<name>` on a `ReactWcHost` (`display: contents`), which registers in `HostRegistry` under the nearest React-rendered ancestor and is portaled into — "the React tree nests like the DOM" (`node-view.tsx:17-38`).
- Lit: `LitComponentApi = WebComponentImplementation`. Angular: `AngularCatalog` takes `AngularComponentImplementation | WebComponentImplementation`; a custom-element-only entry gets the placeholder `UniversalOnlyComponent`; with `useUniversalComponents: true` (default `false`; `true` only under the v1.0 `provideA2UI`) the host mounts the element directly, setting `injector`, `node`, `context` before `appendChild` (`angular/src/core/component-host.component.ts:294, 349-361`). Upstream's add-on catalogs are custom-element-only: VegaChart (`A2uiVegaChartElement extends A2uiLitElement`, light DOM, deps `@a2ui/web_core`, `lit`, `vega*`, `zod`), MCP (`McpAppElement`, `a2ui-mcp-app`), hosted unchanged by the React and Angular explorers.

### A2UIVerse's side
- The loader's export check asks for `CATALOG` with a string id and a components Map, and `Provider`, when present, a function or a `$$typeof` object (`packages/sdk/js/src/catalog.ts:66`); the client holds upstream's custom-element basic catalog through the same `ResolvedCatalog` path with no Provider (`apps/client/src/catalogs/clientCatalogs.ts:82`); navigation reads components off the page by the `A2uiWebComponentElement` contract (`docs/design/client.md`, "Navigation"). Stellify bundles a built ESM entry, externalizes the eight lent specifiers, refuses any other subpath under a host package, checks the `CATALOG` export name (`packages/stellify/src/pack.ts:100-115`, `bundle.ts:48, 56`); `@a2ui/web_core/v0_9/universal` and `lit` are not lent. `isComponentNode` is an `instanceof MutableComponentNode` check (published `src/resolution/component-node.js:28-30`), so a second copy of web_core's universal module in an artifact would not recognise the page's nodes.
- Custom-element tag names are global per document: two builds of one catalog on one page (SPEC §10) or two catalogs sharing a tag meet `registerUniversalElement`'s throw. Lit `static styles` go to `document.adoptedStyleSheets` directly, outside `loadStylesheet`'s per-build `@scope`, and the collision detector sees no shadow-DOM sheet. The mock shops' catalogs are upstream's basic elements under a new id with a sheet and a Provider for the sheet alone.

### Native Angular components inside the React canvas
`@a2ui/angular` 0.13.0 (peer `@angular/core` `^21.2.5`, no `@angular/elements`, no `zone.js`; `SurfaceComponent` `a2ui-v09-surface` takes a `surfaceId` and reads the surface from `A2uiRendererService`'s own `MessageProcessor`, `providedIn: 'root'`). Three blockers, recorded as findings 24, 25 and 26 in `_dev/a2ui-findings.md`:
- `WebComponentNode` assigns `context` in the ref callback, after insertion; `AngularWcHost.connectedCallback` throws without it and its setters never mount later. Measured with React 19.2.8 under jsdom 29.1.1: ref-callback assignment lands after `connectedCallback`; a prop at create lands before.
- `ComponentBinder`'s and `A2uiRendererService`'s constructors call `initializeAngularReactivity`, which `setSignalImplementation`s web_core module-wide; the React renderer's Preact signals then fail `assertAngularSignal`. A second web_core in the artifact fails the other way (`bindNode` → `peekValue(node.props)` on the page's signal).
- Native containers render children as `<a2ui-v09-component-host>`, which looks the surface up in the service's processor and waits forever; actions fall back to it; native entries set no `node`/`context` on the DOM.
What stays possible without `@a2ui/angular`'s host: an artifact bootstrapping a zoneless Angular application (`createApplication` + `provideZonelessChangeDetection`, as upstream's samples run) and wrapping each component as a custom element meeting `A2uiWebComponentElement` — mounting when `context` arrives, binding through web_core's `GenericBinder` (lent under `/v0_9`), `componentRef.setInput` + `detectChanges`, actions from the props' closures, children by tag — with Angular bundled into the artifact. Bundle cost not stated in the repo (raw unminified ESM: `@angular/core` 1.1 MB, `@angular/common` 340 KB, `@angular/platform-browser` 84 KB; `@a2ui/angular` 60-112 KB). The adapter's `spartan-a2ui-adapter` (`@a2ui/angular` 0.8.3, `@a2ui/web_core` 0.8.0, Angular 21.2, zone.js) uses the 0.8-era `{type: () => import(…), bindings: ({properties}) => [inputBinding(…)]}` catalog shape.
